# Independent review of the prospective checkpoint guard

Reviewer: wrapped_scope. This is a static review of a draft guard and staging
installer, not their execution or an installation. The reviewer authored q185,
peer-reviewed q24 and q3100, and reviewed both application candidates. This
review is independent of the coordinator's guard, not all underlying source
and application evidence; source-read credit does not transfer.

The registered guard and installer name the same 25 pin paths. Four installer
hash constants match the captured process ciphertext manifest, process receipt,
application-v2 manifest and v2 root capture. The two root captures name exactly
seven root files; their only row difference is the corrected assessment report.
All seven v2 row byte, SHA-256, Git blob and Git-mode identities match the
previously captured candidate payloads and the captured root wrapper. The
captured application correction and prior independent comparison preserve the
report's draft-time clarification and unchanged before/after/observation
bytes. The guard names the 8ca parent/tree and 95e source/tree and checks four
selected queue rows, a parsed-equal 1,128-entry ledger prefix, the 1,404/2,309
queue counts, and no completion, repair or product validation. Its stronger
application and reconciliation calls have their own scope and dependencies.

A concrete gap exists in the captured draft: the guard admits zero or all four
`closing/` files beyond the stage-capture rows, and the root wrapper executes
`closing/VERIFY.py` when present. When these late files are outside the captured
rows, the guard does not bind their bytes before that execution. An independently
anchored check before execution, or removal of the late path, is needed. The
coordinator has stated an additive successor will remove the path; it was not
part of this review.

The guard compares the stage file set against capture rows plus capture/status
and the optional closing set, rejects symlinks and Python caches, and validates
captured bytes and Git blob hashes. It does not require an exact directory set
or full directory/root modes. For files, it checks the owner executable bit
against Git mode, not every POSIX permission bit. The source-custody wrapper
separately checks any executable bit on its selected receipt files, not original
full receipt modes. The complete stage capture, its independent outer anchor,
installation preflight and any filesystem-mode preservation remain separate.
The guard does not itself assert current HEAD, branch or worktree cleanliness.

The root wrapper and application verifier accept an optional `--predecessor`.
Without it, the nested predecessor guard is not rerun, but the default success
output does not explicitly say so. The index mentions a stronger predecessor
replay without spelling out this default. The coordinator has stated a later
successor will print the supplied/omitted state.

The source and process encrypted verifiers are invoked without keys: they check
ciphertext identities and within-group nonce uniqueness, not authenticated
restoration. The receipt checks compare captured, recorded restoration results;
they do not repeat decryption or independently establish key custody. The
prior nonce inventories are not passed, so cross-scope uniqueness is not
rechecked in these invocations. Public source transports and peer verifiers
check their registered member identities and recorded results, not source
semantics or new product-source reads. The index correctly qualifies the
same-machine key, prior ciphertexts and Git objects as separate dependencies.

At initial capture `later-encrypted/`, `later-receipt/`, the final staged guard,
stage capture and installation status were unavailable. Their names and
intended calls can be inspected in the draft, but their actual interfaces,
contents, modes and eventual complete file set are not verified here. The
index's references to those later groups are prospective at this cutoff. The
installer computes most pin values from then-current files; it pins four values
explicitly but does not independently pin its own draft guard bytes. It creates
the destination and writes guard, pins and result sequentially, so a later
failure may leave partial staging artifacts. Any preinstallation action and
failure record need their own verification and custody.

The index retains the point-in-time main observation, missing checkpoint 3821,
separate recovered and reconstructed 059 and normalized 774 attributions,
SOURCE004 and 73 nontext/no-positive-EOF obligations, and incomplete thirteen
lenses. Seven planning relationships are not a unique-defect count. No guard,
installer, product, build, test or runtime probe was run in this review. The
105 captured files were rehashed in a second pass rather than atomically;
later external Git/key and restored originals remain separately held. A finite
privacy scan cannot exclude all encodings.
